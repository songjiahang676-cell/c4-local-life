# Repository Instructions for Coding Agents

## Scope

This repository is the implementation baseline for 南加生活网 / SoCal Life Platform. Follow these rules for every directory unless a deeper `AGENTS.md` explicitly narrows them.

## Architecture boundaries

1. `apps/web` and `apps/admin` may call the public API or server-side application clients; they must not import Prisma or database adapters.
2. `apps/api` owns synchronous business use cases. Controllers validate/authorize and delegate; domain/application services enforce invariants; repositories own persistence.
3. `apps/worker` owns retryable asynchronous jobs. Every handler must be idempotent and safe under duplicate delivery.
4. `packages/database` contains schema, migrations, generated client setup and repositories; it must not contain HTTP concerns.
5. `packages/contracts` contains serializable shared contracts only. Do not place server secrets, database models or UI components there.
6. PostgreSQL is canonical. Redis and OpenSearch must be rebuildable from canonical data plus outbox/event history.
7. Cross-module writes happen through application services or explicit events; never reach into another module's tables from a controller.

## Required commands

Before handing off a change, run all commands that are possible in the environment and report exactly what ran:

```bash
bash scripts/check-architecture.sh
pnpm format:check
pnpm db:validate
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

Run targeted tests during development, then the broad suite before a Gate or release. Never claim a command passed when it was not run.

## Coding rules

- TypeScript strict mode stays enabled. Do not use `any` except at a deliberate adapter boundary with a narrowing test.
- Prefer named exports, small modules and explicit return types at public boundaries.
- Use UTC instants in storage; render with the user's IANA time zone. Default product zone is `America/Los_Angeles`.
- API identifiers are UUIDs. Public slugs are not authorization identifiers.
- Money is integer minor units or fixed-precision decimals plus ISO currency; never IEEE floating point.
- All mutating endpoints support an idempotency strategy where retries are plausible.
- Errors exposed over HTTP use RFC 9457-style Problem Details and never leak stack traces or raw provider errors.
- Log structured fields; do not log session tokens, OTPs, passwords, full payment details or raw PII.
- Every database migration is forward-safe, reviewed and accompanied by rollback/roll-forward notes.
- New user-visible strings must be localizable. Do not concatenate translated fragments.
- Preserve semantic HTML, keyboard operation, focus visibility and meaningful accessible names.

## API and contracts

- `openapi/openapi.yaml` is the REST contract. Add or change it with the implementation and contract tests.
- Use cursor pagination for mutable/high-volume lists; offset pagination is allowed only for bounded admin reports.
- Return resource versions/ETags for concurrent edits where overwrites matter.
- Use `Idempotency-Key` for payment, order, promotion purchase and other externally retried writes.
- Webhooks require signature verification, replay protection, durable receipt and asynchronous processing.

## Data and privacy

- Collect only fields required by a documented purpose.
- Exact addresses, phone numbers and emails are private by default and exposed through policy-controlled views.
- User deletion is a workflow, not an uncontrolled cascade. Preserve legally/audit-required financial records while de-identifying public profile data.
- Test tenant/organization boundaries and object-level authorization on every new resource.

## Testing

For each feature, cover the useful layers:

- pure domain rules with unit tests;
- repository behavior with PostgreSQL integration tests;
- API contract and authorization tests;
- worker idempotency/retry/dead-letter behavior;
- critical journeys with Playwright;
- accessibility checks for public templates;
- abuse/security cases for auth, messaging, upload, review and payment paths.

Do not rely primarily on snapshots for business behavior.

## Change discipline

- Work from a task ID in `tasks/BACKLOG.csv`.
- Keep changes reviewable and avoid unrelated formatting churn.
- Update the relevant docs, diagrams, OpenAPI, JSON Schema, seed data and acceptance criteria in the same change.
- Add an ADR for material architecture decisions; do not silently overturn an accepted ADR.
- Generated files must be regenerated by documented commands, not hand-edited.
- Do not commit build output, local object-store data, database dumps, `.env`, credentials or customer data.

## Completion report

Include task ID, changed files, contract/migration impact, tests actually run, security implications, observability changes, documentation updates and known gaps.
